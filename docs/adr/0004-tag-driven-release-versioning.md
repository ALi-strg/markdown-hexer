# Tag-driven release versioning and asset naming

Releases are tagged `v1.0.x`, but the version baked into every bundle came from the static manifests (`0.1.0`), so a `v1.0.3` release shipped `Markdown-Magic_0.1.0_*` assets that were also indistinguishable across platforms. The Version is now resolved from the triggering git tag at build time (leading `v` stripped, prerelease tags like `v1.1.0-rc.1` flag the Release as prerelease) and injected via a build-time config file (`--config .release-version.json`) rather than by mutating the manifests, so the manifests keep a static dev version that never ships and there is no version drift to manage. Inline JSON was rejected because GitHub's `format()` function rejects JSON braces in format strings. The pipeline runs only on pull requests into main and on `v*` tag pushes — a plain push to main triggers nothing. Uploaded assets are renamed via tauri-action's `releaseAssetNamePattern` to `Markdown-Magic_<version>_<platform>-<arch><setup>.<ext>` with the platform written literally (`windows` / `macos` / `linux`) because the action's `[platform]` placeholder yields `darwin`/`linux`. `productName` is deliberately left untouched: the MSI upgrade code is derived from it, so overriding it per platform would silently break upgrades of already-installed MSI packages. Historical releases keep their original asset names.

The rename as first implemented silently never applied: the workflow pinned `tauri-apps/tauri-action@v0`, whose rename input is named `assetNamePattern`, while `releaseAssetNamePattern` only exists in tauri-action v1.x — unknown inputs on a JavaScript action are dropped without error, so assets shipped under Tauri's default bundle names (`Markdown-Magic_1.1.2_aarch64.dmg`, which embed Version and arch but no Platform Label). The action is now pinned to `@v1` (which reads `releaseAssetNamePattern`), restoring the naming this ADR describes. This is why the naming decision predates the working implementation.
