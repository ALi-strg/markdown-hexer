# Markdown Hexer 2.0 framework spike

Raw evidence for the toolkit decision in
[ADR-0017](../adr/0017-toolkit-selection.md). The spike crate, fixtures,
screenshots and CSV logs were throwaway and stayed outside the repository.
Every number below comes from those logs; none is estimated.

## Method

The egui spike was built in release mode with `opt-level = 3`, `lto = "fat"`,
`codegen-units = 1`, `panic = "abort"` and `strip = true`. eframe 0.37 was
configured with glow, AccessKit, clipboard, links and system fonts, with
default features off. No wgpu, no webview.

**Startup.** An external Python harness launched the executable 20 times,
polled Win32 for the visible top-level window (T1), then captured the client
area every few milliseconds and waited for at least 250 dark pixels in the
text region (T2, readable document). First launch after the build was excluded
as a warm-up. The T2 capture path adds roughly 5–20 ms of polling and screen
grab overhead, so it slightly overstates readability. The window was
1440 × 900, Light palette, README fixture.

**1.5.0 baseline.** `v1.5.0` was checked out into a separate worktree, its
frontend built with the repository's lockfile, and its Tauri app compiled with
`cargo build --release` (1 m 14 s). The same external harness ran 20 launches
with warm page cache and a warm WebView2 profile. The app presented its
default `Untitled.md` window. Cold-disk startup could not be measured: the
session is non-admin and has no standby-list/cache-drop tool, so the
owner-reported 7–10 s cold start is recorded, not reproduced.

**Editor.** The spike switched from Preview to Edit after two preview frames,
timed the first Edit build/render, then injected text events, undo commands,
shift-selection events and scroll frames. Frame deltas came from eframe's
frame counter. The 100 KB fixture is 105,503 bytes / 5,000 lines; a smaller
102,969-byte / 1,480-line fixture was also measured. The 20 first-Edit runs
used 600 text events and 120 scroll frames; a separate 3-run sustained test
used 1,500 text events, 20 undo, 20 selection and 600 scroll frames (2,145
frames, about 15 s at 143 Hz). Percentiles use linear interpolation between
order statistics.

**CJK.** The editor received `ImeEvent::Preedit`, `ImeEvent::Commit` and a
plain `Event::Text` with mixed Japanese, Chinese, Korean and Latin text. This
tests egui's composition plumbing and glyph fallback, not the OS candidate
window.

**Accessibility.** An `egui_kittest` harness rendered the preview and dumped
the AccessKit tree, then sent Tab and inspected the focused node. The test is
in the throwaway crate, not in this repository.

## Startup results

| Run set | T1 p50 | T1 p95 | T1 min / max | T2 p50 | T2 p95 | T2 min / max |
|---|---:|---:|---:|---:|---:|---:|
| 1.5.0, 20 warm launches | 5,229.4 ms | 5,241.7 ms | 5,217.4 / 5,247.3 | 5,266.9 ms | 5,278.3 ms | 5,249.6 / 5,297.7 |
| egui spike, run A, 20 launches | 134.8 ms | 151.9 ms | 129.0 / 154.2 | 168.0 ms | 182.5 ms | 158.0 / 185.6 |
| egui spike, run B, 20 launches | 131.7 ms | 138.4 ms | 125.0 / 142.5 | 165.2 ms | 172.2 ms | 156.6 / 175.8 |
| egui spike, CJK fixture, 10 launches | 132.6 ms | 138.9 ms | — | 162.9 ms | 173.1 ms | — |

Readable startup improved by about **31× at p50** (5,267 ms → 168 ms) and
about **29× at p95** using the slower of the two egui runs (182.5 ms). The
Windows readable gate is 200 ms p95; both egui runs pass, and the repeat run
measured 172.2 ms.

Internal instrumentation attributed the egui number: main entry to first-frame
start was 9.1–9.7 ms, and second-frame start was 9.7–10.4 ms over 3 runs. The
remaining ~125 ms is OS process creation, DLL loading, window mapping and
first presentation, not Markdown rendering. The first visible window (T1)
already appears at ~135 ms; document text is detectable ~33 ms later.

The 1.5.0 result **corrects the warm number, not the cold claim**: 5.27 s warm
is already far above the 200 ms gate. The owner's 7–10 s cold figure remains
plausible; this session could not clear the file cache to reproduce it.

## Editor results

| Fixture | Bytes / lines | First Edit | Notes |
|---|---|---:|---|
| 100 KB class | 102,969 / 1,480 | 12.30–12.49 ms | 3 runs |
| 100 KB class | 105,503 / 5,000 | p50 136.3 ms, p95 146.4 ms, max 218.0 ms | 20 runs; first run 218.0, remaining 128.4–142.7 |
| 5,000 lines | 220,817 / 5,000 | 140.4–144.2 ms | 3 runs |
| 5,000 lines (superseded padding) | 275 KB / 5,000 | 145.0–151.8 ms | 5 runs |

The first-Edit gate is 150 ms for a 100 KB document. The 5,000-line case
passes at p95, but the first run after the build exceeded the gate at 218 ms.
That outlier is recorded, not hidden; its cause was not isolated, and it is the
main cold-start risk for Edit.

Interaction on the 105 KB / 5,000-line document over 2,145 frames (about
15 s at 143 Hz), including 1,500 typed characters (about 10.5 s) and 600
scroll frames (about 4.2 s):

| Operation | p50 | p95 | Max |
|---|---:|---:|---:|
| Typing per frame | 1.06–1.09 ms | 1.24–1.28 ms | 1.92 ms |
| Undo per frame | 0.09–0.10 ms | 0.10–0.14 ms | — |
| Selection per frame | 0.09–0.11 ms | 0.11–0.12 ms | — |
| Scroll per frame | 0.10–0.11 ms | 0.11–0.15 ms | — |
| Frame delta (whole run) | 6.94 ms | 7.11–7.20 ms | — |

Frame p95 stayed below 7.5 ms against the 16.7 ms 60 fps budget. The display
runs at 143 Hz, so the 6.94 ms p50 is vsync-bound. The shorter 20-run sweeps
measured the same frame p95 range (7.11–7.42 ms), so sustained typing did not
degrade.

## CJK

- Glyph fallback: Japanese, Chinese, Korean, emoji and arrows rendered
  correctly in Light and Dark once system fonts were enabled. No font bundle
  was added.
- Composition plumbing: `ime_ok = true`. The injected preedit was followed by
  a commit and the editor contained `日本語` plus the mixed-text payload
  (`len = 105,560` on the 5,000-line fixture).
- First Edit with the CJK fixture: 134.1 ms. Frame p95 during the run was
  12.2–15.4 ms, still under 16.7 ms.
- **Unverified:** native IME candidate-window placement, candidate selection,
  and real keyboard input from a Japanese/Chinese IME. This environment cannot
  automate the OS candidate UI.

## Accessibility

`cargo test --release accesskit_tree` passed. The tree contained:

| Role | Count |
|---|---:|
| Window | 1 |
| Button | 38 |
| Link | 7 |
| Image | 1 |
| Label | 306 |
| GenericContainer | 159 |

Section titles and chevrons appear as Buttons (`Features`, `v`), Code Copy
controls as Buttons named `Copy`, links as Links with accessible names, and
the image as an Image node. After one Tab, exactly one node was focused: the
first chevron Button labelled `v`. So a keyboard focus path exists.

Limitations:

- No Heading role. Collapsible headings are buttons by construction.
- Table and list structure flattens to Labels; there are no row/column or
  list-item roles.
- The image node reported the relative-path failure
  `Failed loading file://AppReadme.png: Der angegebene Pfadname` because the
  spike did not yet rewrite paths against the document directory.
- The kittest used Segoe UI as a fallback and allowed missing glyphs; the
  production font stack will differ.

This is basic, not sufficient, accessibility. Custom AccessKit nodes or a
different Section control are product work.

## Preview coverage

The README fixture was shown in Light, House, Dark, High Contrast, Nord,
Terminal Green and System at two scroll offsets. Screenshots are in the
throwaway evidence directory (`palette-<key>-<offset>.png`).

| Feature | Result |
|---|---|
| Headings, nested Sections | Works via the app-side splitter; chevrons collapse and expand. Headings are indented 28 px relative to body because the chevron is in flow. |
| Code Copy | App-rendered button, language label, toast and `ctx.copy_text`. Clipboard paste-back was not exercised end to end. |
| Tables | GFM table renders with striped rows. No cell borders and no bold header; plain enough to read at 15 px. |
| Strikethrough, task lists, footnotes | Render. Task checkboxes are glyphs, not interactive controls. |
| Raw HTML | Shown as literal text (`<b>...</b>`), not rendered or executed; ADR-0016 allows text or omission. |
| Code colors | Placeholder regex highlighter; tokens inside comments can still be colored. Not production quality. |
| Images | Absolute `file:///C:/.../AppReadme.png` loads at 1280 px. Relative `AppReadme.png` becomes `file://AppReadme.png` and fails. A document-directory resolver is required. |
| Links | Styled and exposed as Link nodes. Actual browser launch was not exercised. |
| Selection | egui labels are selectable. Automatic Copy-on-Select was not implemented or tested. |
| Palettes | All seven keys apply consistently: background, surface, ink, accent, code background, selection and syntax colors. High Contrast and Terminal Green are intentionally extreme; the small chevron glyph is the weakest control in several palettes. |

Visual gaps recorded: heading indent, table borders/header weight, faint
chevrons in some palettes, code comment coloring, relative image gap, and no
syntax theme mapping beyond the placeholder palette.

## Binary

`hexer-spike.exe`: **8,836,096 bytes (8.84 MB)**. Target ≤ 20 MB: pass.
This excludes any WebView2 runtime, which the native app does not need.

## Recommendation

**Go with egui 0.37 + glow.** The Windows startup, binary-size, first-Edit and
60 fps gates pass with the caveats recorded above. iced 0.14 is not a
justified pivot: its default wgpu renderer would need a tiny-skia-only
configuration this spike did not measure, and it has no better accessibility
evidence from this spike.

Do not treat the spike as a shippable preview. Before 2.0:

1. Verify Linux Wayland and macOS startup, glow/GL behavior and font fallback.
2. Verify a real CJK IME candidate window and Copy-on-Select.
3. Add document-directory image resolution and link activation tests.
4. Replace the placeholder highlighter and add Heading/table/list AccessKit
   semantics, or narrow the accessibility acceptance criteria explicitly.
5. Measure cold-disk startup on a machine where the cache can be dropped.
