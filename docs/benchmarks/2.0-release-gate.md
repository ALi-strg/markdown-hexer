## Method

Startup and First Edit are external measurements; the app timestamps are only
used as a cross-check.

- T1: the launched process's first visible window whose title matches
  `<fixture> — Markdown Hexer`, polled through Win32 `EnumWindows` and
  `IsWindowVisible` every 2 ms (`app/tools/startup_bench.py`). Launch time is
  taken immediately before `CreateProcess`.
- T2: the app writes its own timestamp when the first frame containing the
  rendered document is submitted. The shell is created hidden, so that frame is
  painted before the window becomes visible; T1 is the first moment it can be
  on screen. The external T2 subtracts that Unix timestamp from the launch wall
  clock; the in-app T2 is measured from `main` and is a lower bound (it misses
  process creation and DLL loading).
- First Edit: launch Preview on the 105,503-byte, 5,000-line fixture, press
  Ctrl+E, and stop at the end of the first editor frame
  (`app/tools/first_edit_bench.py`).
- Editor frames: `app/examples/editor_5k_bench.rs` drives the real `HexerApp`.
  Five seconds of warm-up typing at the chosen anchor, then ten seconds at
  ~144 fps: 3 s of typing, 3 s of Shift+Right selection, 4 s of wheel
  scrolling. Each frame's `frame.info().cpu_usage` is recorded; the budget is
  16.7 ms of CPU time per frame. The process runs at `HIGH_PRIORITY_CLASS` to
  match a foreground window.

Commands, from `app/`:

```sh
cargo build --release --all-targets
python tools/release_gate.py
```

`release_gate.py` runs the gates below and prints one pass/fail table. It calls
the three measurement scripts, whose raw CSVs stay in
`app/target/bench-logs/{startup,first-edit,editor}/`.

The 2 ms polling interval quantizes external T1 to 2 ms steps, which is why its
median and p95 can repeat; T1 and T2 can also swap order within one interval.
Both stay well under 200 ms in every run of both font gates.

The Serif run used `--font serif`, which writes
`{"version": 1, "theme": "light", "font": "serif", "text_size": "medium"}` to a
throwaway `%APPDATA%\markdown-hexer\settings.json` inside the benchmark's temp
directory. The user's real settings file was never written.

## Editor, 5,000 lines

Both anchors, five runs each, `python tools/editor_bench.py --runs 5 --anchor
{end,start}`. "start" puts the cursor at the top of the fixture before the
warm-up, so the first paragraph gains wrapped rows on every keystroke and every
paragraph below it has to be re-laid out; "end" is the protocol the earlier
benchmark used.

| Run | Frames | p50 | p95 | Worst frame | Over 16.7 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| end 0 | 1,439 | 1.17 ms | 1.94 ms | 2.19 ms | 0 |
| end 1 | 1,438 | 0.53 ms | 1.99 ms | 2.43 ms | 0 |
| end 2 | 1,439 | 1.14 ms | 1.96 ms | 2.39 ms | 0 |
| end 3 | 1,440 | 1.12 ms | 1.96 ms | 2.53 ms | 0 |
| end 4 | 1,441 | 1.12 ms | 1.93 ms | 2.43 ms | 0 |
| start 0 | 1,439 | 0.60 ms | 1.95 ms | 2.25 ms | 0 |
| start 1 | 1,433 | 0.57 ms | 1.96 ms | 3.01 ms | 0 |
| start 2 | 1,440 | 0.53 ms | 2.00 ms | 2.31 ms | 0 |
| start 3 | 1,441 | 1.12 ms | 1.94 ms | 2.34 ms | 0 |
| start 4 | 1,436 | 0.54 ms | 2.21 ms | 2.97 ms | 0 |

All ten runs recorded 10 s (±10 ms) of frames at the display's 143 fps. The
"start" p50 is lower than "end" because the measured window mixes typing,
selection and scrolling; the p95 and worst frames are the comparison that
matters, and they are equal.

Attribution: the earlier note said epaint's paragraph cache keys each child by
the remaining `max_rows`, so a growing first paragraph invalidates every later
paragraph. That is not what happens on epaint 0.37 with this highlighter. The
highlighter sets `job.wrap.max_width` and leaves `wrap.max_rows` at its default
(`app/src/editor.rs:338-342`); the galley cache splits on `\n` but every child
copy still carries `max_rows: usize::MAX`, because
`max_rows_remaining` only decreases once it differs from `usize::MAX`
(`epaint-0.37.0/src/text/galley_cache.rs:149,167,229-230`). A row-count change
therefore does not invalidate the later paragraphs. The cost left is the
app-owned cache: one `LayoutJob` for the whole document whenever the text hash
changes (`app/src/editor.rs:328-372`), which measures ~2 ms p95 at 100 KB /
5,000 lines.

The benchmark now exposes `HEXER_EDITOR_BENCH_ANCHOR=start|end`
(`app/tools/editor_bench.py --anchor`), so the end-only protocol is gone.

## Startup path audit

- Renderer: `eframe` is built with `default-features = false` and the `glow`
  feature (`app/Cargo.toml:20-22`), `Renderer::Glow` is set in
  `app/src/main.rs:41`, and `cargo tree -i wgpu` prints nothing. No wgpu code
  is compiled or linked.
- Network: `ureq` is in the graph only through `egui_extras`' remote-image
  feature (`cargo tree -i ureq`); the app does not install egui's image
  loaders. On the first frame remote images are rendered as their Markdown
  source (`app/src/preview.rs:161-176,477-479,508-512`) and
  `NativeImageSource` resolves only local paths (`app/src/image.rs:23-40`).
  Nothing in the startup path calls `ureq`/`ehttp`.
- Update and telemetry: no updater code; the only IPC is the single-instance
  handoff over a per-user local socket / named pipe, with no TCP port
  (`app/src/platform/instance.rs:1-6`).
- System fonts: `install_fonts` reads a fixed list of known file paths, one
  read per family (embedded default font, the selected content face, and one
  CJK fallback); it never enumerates the font directory
  (`app/src/ui/mod.rs:136`). An A/B run with those reads disabled (temporary
  env hook on the 0d979a5 tree, raw output in
  `app/target/bench-logs/summaries/startup-nofonts.txt`) measured
  8 ms of the in-app T2 (112.2 ms → 104.3 ms median), so the eager reads are
  inside the budget measured above. Known deviation from the spec's
  "CJK/emoji fallback resolves on demand": the CJK fallback face is read on
  the first frame even for Latin documents. It is a single bounded read of
  `YuGothR.ttc` (13.8 MB), not a scan, and it buys preedit rendering without a
  font install mid-session; the 8 ms above is its cost. Flagged for the spec
  owner rather than changed here because a lazy install resets the font atlas
  and would render the first IME preedit on a frame with no CJK glyphs.

## Cold-disk startup: UNVERIFIED

Not measured. Dropping the Windows file cache requires clearing the standby
list, which needs `SeProfileSingleProcessPrivilege`; this session is not
elevated (`IsInRole(Administrator)` is false) and no standby-list tool is
installed. Calling a warm run "cold" would be false, so the ≤ 700 ms gate stays
unverified.

Reproducible method:

1. Elevated PowerShell: `RAMMap.exe -Et` (Sysinternals) or
   `EmptyStandbyList.exe standbylist`, then confirm standby memory is near zero
   in RAMMap.
2. Within the next few seconds run
   `python app/tools/startup_bench.py --runs 5`; run 0 is the cold launch.
   Alternatively reboot and immediately run the same command before anything
   else touches the files.
3. The cold set is the 8.6 MB exe, the ~15.5 MB of font files, and the fixture.

Upper bound, not a measurement: those reads are ~24 MB from an NVMe SSD, on the
order of 10 ms of I/O, so the 700 ms budget is not plausibly at risk from the
startup reads alone. It still needs the run above before it can be claimed.
