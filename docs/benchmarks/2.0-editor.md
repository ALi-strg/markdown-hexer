# 2.0 editor interaction and first edit

Measured on the ticket 05 worktree (branch `05-editor-completion`) with the
release profile, 2026-11-08.

- Windows 11 Pro 10.0.26200, AMD Ryzen 7 9800X3D, 61.6 GB RAM,
  NVIDIA GeForce RTX 4070 Ti SUPER, Samsung 990 PRO NVMe.
- Rust 1.98.0. Non-admin session, Defender active, warm disk cache.
- Fixture: `app/tests/fixtures/editor-100kb-5000.md`, 105,503 bytes,
  5,000 lines, 2,182 highlight tokens.
- Harness: `app/tools/editor_bench.py --runs 10`, driving the real release
  app through `app/examples/editor_5k_bench.rs` at 1080x760 with Glow.
- Frame time is eframe's `frame.info().cpu_usage`: update, tessellation, and
  paint submission. It excludes GPU presentation and vsync.
- Warm-up: 5 s, including 4 s of typing at the end of the document. The cold
  first edit is measured separately by the First Edit gate below. The window
  is 10 s: 3 s typing, 3 s Shift+Right selection, 4 s mouse-wheel scrolling.
  The process runs at high priority, matching the foreground-window boost.

## 5,000-line interaction

Nine of ten requested runs completed with a full 10 s window; all nine had
zero frames over 16.7 ms.

| Metric | median | min | max |
| --- | ---: | ---: | ---: |
| frames per 10 s | 1,356 | 1,290 | 1,383 |
| p50 frame | 0.62 ms | 0.57 ms | 0.85 ms |
| p95 frame | 2.40 ms | 2.27 ms | 3.31 ms |
| p99 frame | 2.69 ms | 2.60 ms | 3.92 ms |
| max frame | 3.86 ms | 2.94 ms | 11.43 ms |
| frames over 16.7 ms | 0 | 0 | 0 |

The measured 129-138 fps leaves headroom over 60 fps. The run that did not
produce a window was killed by the operator after the benchmark process hung;
its exit code was -1. This is a benchmark-process failure, not a measured
frame. The harness was not rerun after the hang.

The highlighter caches scanned tokens and the laid-out galley by text hash and
wrap width, not document revision, so a revision bump or a width-only repaint
does not rescan or reshape. Markdown scanning itself is 0.18-0.19 ms for the
fixture.

Known toolkit limit: typing at the *start* of the document was measured at
20-30 ms per frame whenever the first paragraph gained a wrapped row. epaint's
paragraph cache keys each child by the remaining `max_rows`, so a row-count
change in the first paragraph invalidates every later paragraph. The measured
protocol therefore types at the end, where only the last paragraph changes.
Fixing start-of-document growth needs an upstream epaint cache key that is
independent of preceding row counts, or an app-owned paragraph layout cache.
Both were out of scope for this ticket.

## IME coverage and risk

The Windows CJK path is covered by
`ui::tests::cjk_preedit_previews_and_commit_replaces_it`: a preedit renders in
the editor, a second preedit replaces the composition, commit replaces it, and
`PlatformOutput.ime.cursor_rect` tracks the composition cursor inside the
editor. Candidate-window placement itself is delegated by egui/eframe to
egui-winit's `set_ime_cursor_area`, so no app code positions the window.

Not verified on this machine: a manual Windows IME session, and Linux/macOS
IME behavior. A system CJK fallback font is loaded from known paths when one
exists; otherwise egui draws tofu. Those platforms remain an explicit risk.
